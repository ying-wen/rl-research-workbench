# 一轮研究如何结束，下一轮如何开始

把“持续优化”落实为有预算、有版本、有反证的连续研究。上一轮留下的不只是最优 checkpoint，还包括为什么改变算法、所有候选和失败、哪些数据已经看过。迭代次数不是科学证据；保留下来的判断应逐轮变得更明确。

## 阶段、出口与退回规则

| 阶段 | 开始前必须有 | 本阶段只解决 | 出口；未通过时 |
|---|---|---|---|
| 问题 | 实际失败现象、强先行方法 | 原目标与现有缺口 | 写出能推翻主张的结果；否则缩小问题 |
| 设计 | 研究卡、信息权限 | 为什么这一项修改可能有效 | 推导、竞争解释、最小正反例齐全；否则不扩建代码 |
| 正确性 | 伪代码与测试预期 | 实现是否忠实 | 边界和参考结果通过；错误修复不算性能贡献 |
| 机制 | 可控干预与诊断指标 | 修改是否沿预测路径起作用 | 中介预测成立或解释被修订；不自动进入大基准 |
| 开发 | 有限搜索空间、预算 | 哪个配置值得确认 | 完整矩阵、选择规则和资源账齐全；保留失败配置 |
| 确认 | 版本锁定、新独立样本 | 在预定目标分布上效果多大 | 按精度/样本计划结束；结果不佳也结案 |
| 决策 | 效果、区间、失败、成本 | 保留、修订、扩大或停止 | 写决策及新问题；不静默重开确认集 |

阶段可缩短，但其判断不能合并。例如一个可手算更新无需大规模测试；一个新深度算法不能用小 MDP 等式校验替代闭环控制证据。资源不足时减少主张范围，记录尚未完成的阶段。

## 版本 A → 诊断 → 最小修改 → 版本 B

以下为设计例子，未声称实际运行结果：

1. A 在奖励尺度变大后出现 critic 更新尖峰和回报下降。先查奖励、终止和归一化实现；记录“优化尺度”与“行为探索变化”两种解释。
2. 固定同一经验序列，比较 A、降低学习率、仅更改 critic 的候选 B。测量实际更新范数、TD 误差、参数有限性。若 B 只因平均更新变小受益，需要加入幅度匹配对照。
3. 回到交互，固定任务分布与数据预算；测试 B 是否减少尖峰并改善后续回报。固定数据结果只支持计算或估计器性质。
4. 若同时改 actor 与 critic，使用 2×2：都不改、只改 actor、只改 critic、两者都改。解释交互项，并为整个方法安排完整对手。
5. 在开发数据上分别完成 A、B 的调参。预设选择规则，保留未胜出的配置及代价。锁定 B 后，用新种子或新生命期确认。
6. B 若未达到实际价值门槛，记录“该机制在这些条件下成立，但控制效益尚未确立”，或明确负效果。不要只留下少数胜出的任务；下一轮应改变可检验解释，而不是改图表范围。

## 两套基线不能互相替代

**完整方法比较**回答可部署算法之间的表现。保留作者定义的网络、优化器、奖励处理、数据访问和关键超参，对每个方法给予清楚的调参预算；改动原方法就改名并说明。

**共同基座控制**回答机制归因。在统一网络和训练环中移植一个模块，可以隔离更新、输入或时序，但应命名为“基座 + 模块 X”，不能冒充作者完整算法。固定原超参删除组件与给每个删减版重新调参，分别回答局部依赖和算法族可达性能。

## 每轮的有限资源合同

把预算分为查错、机制、搜索、确认四项，记录上限和已用量。是否增加预算应依据尚缺的证据：覆盖不足、精度不足或需要独立确认；不得因为候选暂时领先就延长其运行，或只等有利 seed 完成。

故障先分身份：基础设施故障允许按统一重跑规则新增 attempt，并保留原 attempt；算法数值失败计入失败分析；未知状态先核日志和进程，不能盲目重试。计划总数、完成数、失败数和未完成数同时报告，禁止只比较幸存运行。

## 交接与下一轮

每轮更新[迭代日志](../templates/iteration-log.md)和[决策记录](../templates/decision-record.md)。交接应能回答：当前问题、固定版本、实际完成的工作、最强反证、未决不确定性、唯一建议下一步。原始数据、锁文件和旧决策不覆盖。

`next` 是创建后继研究的工具，不是批准继续烧算力。只有选择了下一问题、相应预算仍在章程内，才创建新 study。新研究引用父研究与决策；修改后重做受影响的验证，并登记旧确认数据已被使用。达到预算、主张被反证或预计新增数据不能改变决定时停止该方向，保留可复用的环境、负例与算法诊断。

实际命令的输入是父研究**锁文件**。以下路径为本项目可采用的命名示例，先创建相应研究和决策文件：

```bash
.venv/bin/python -m rlworkbench next studies/development.lock.json \
  --decision decisions/current.json --study-id development-v2 \
  --out studies/development-v2.json
```

机器决策包含 `parent_study_id`、`action`、`rationale`、`evidence`；`action` 为 `continue`、`revise`、`confirm` 或 `stop`。确认还需 `selected_arms`，保留基线和候选；工具从开发协议的 `holdout_seeds` 取新种子。种子被预留不代表任务也已独立，仍需人工审查任务/生命期分布。`smoke` 不可直接升为科学确认；`stop` 不生成后继。新 study 仍需阅读、修改、验证和冻结后才能运行。

依据：[Empirical Design in RL](https://jmlr.org/papers/v25/23-0183.html)、[Evaluating the Performance of RL Algorithms](https://proceedings.mlr.press/v119/jordan20a.html)、[Implementation Matters](https://arxiv.org/abs/2005.12729)。完整证据脉络见[调研手册](research-handbook.html#ops-workflow)。
